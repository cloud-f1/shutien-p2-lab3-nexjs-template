Fork 後可整個資料夾改名（例：shutien/）→ 指令變 /shutien:spec。只改一個資料夾。

/athena:spec

Command · L1

OpenAPI-first 規格設計。先編輯 docs/openapi.yaml，再 spawn @spec-writer 產 epic .md + 測試計畫。

強制契約

Stop verifier Rule #6（OpenAPI drift）會拒絕「改了 server / client 但 spec 沒動」的 commit。

典型輸出

新 endpoint 規格 + schema + docs/epics/e{N}-{slug}.md + TDD 第一輪紅燈測試清單。

/athena:implement

Command · L1

TDD 紅綠重構。從 spec → 寫測試（紅）→ 寫最少 code（綠）→ 重構。

強制規則

  • 測試先行：無測試的 code 會被 Stop verifier 擋
  • mock depth ≤ 5 / file（Rule #11）
  • Coverage ≥ 80%（by @qa Phase 2）

/athena:qa

Command · L1 + Pipeline · L4

三合一品質 gate。3 agent 分工：@reviewer（audit）+ @qa（test + coverage）+ @evaluator（E147 獨立驗收）。

Phases（post-Phase 40 會多 2.5 / 2.6）

  • 1 · Static checks (ruff / mypy / eslint)
  • 2 · Tests + coverage ≥80%
  • 2.5 · Contract Conformance (E156 計畫)
  • 2.6 · Migration Safety (E157 計畫)
  • 3 · Test Quality Audit
  • 4 · @evaluator 獨立驗收

Flags

--review-only · --test-only · --eval-only · 不加 flag 則三相順序執行。

/athena:loop

Command · L1

Epic orchestrator — 每次呼叫推進**一步**。讀 docs/epics/EPIC_INDEX.md 和 docs/context/epic-progress.md 找下一個未完成 step。

Step 序列

spec → implement → qa → commit → merge

模式

  • 無參數：推進下一步
  • status：show 當前 state，不執行

/athena:batch

Command · L1

平行執行 — 根據 dependency 圖分 wave，一 wave 內 epic 全部併發。

併發策略

  • Max 4 concurrent agents per wave
  • 每 agent 在獨立 worktree（scripts/hooks/worktree-setup.sh）
  • Wave 完成 → 整合測試 gate（E91）→ 下一 wave

模式

auto（偵測 phase）· --phase N（特定 phase）· 指定 epic list

/athena:plan

Command · L1 · 人類 Gate

策略規劃 → @strategist 審視 codebase 和 recent activity → 提出 epic 提案 → 人類批准 才進 EPIC_INDEX。

Input signals

  • 近期 debug-log（重複出現的 bug → 可能是新 epic）
  • Review findings（系統性問題）
  • 產業信號（如 Phase 41 靠 OpenMythos/RDT/Drafted）

Output

Phase PRD + 若干 e<N>-<slug>.md 草稿 + dependency 圖更新。

/athena:deploy

Command · L1

Zeabur 部署。@deployer 跑 7-gate 協議，任一失敗就 abort。

7 Gates

  1. CI 綠（tests + coverage + lint）
  2. No uncommitted changes
  3. On main branch（或 preview flag）
  4. Migration dry-run OK
  5. Pre-deploy guard pass（scripts/hooks/pre-deploy-guard.sh）
  6. Env vars present（特別是 VITE_API_URL build-time baked）
  7. Rollback plan recorded（deploy-log.md）

每個 .claude/agents/*.md 是一份職位說明書 — 角色、模型、允許工具、write-back 檔案。

Epic Pipeline

Pipeline · L4 · 主力流程

spec → implement → qa → commit → merge

Loop Pipeline

Pipeline · L4 · 單步推進

/athena:loop 讀 docs/context/epic-progress.md，找下一個 ⬜ step，推進 **一步**。

5 steps

  1. spec → spawn @spec-writer
  2. implement → TDD harness (auto @debugger on fail)
  3. qa → QA Pipeline (4-phase)
  4. commit → git commit (Stop verifier 全檢)
  5. merge → git push + gh pr create

為何一步就好

人類在步與步之間有 checkpoint。失敗時不會污染後續步驟。亦是 E164 autopilot 的基礎單位。

Flags

  • 無參數：推進一步
  • status：只讀、不推進

Batch Pipeline

Pipeline · L4 · 平行波次

Max 4 concurrent agents。每個在獨立 git worktree 跑 epic pipeline。

Flow

  1. @orchestrator 讀 dependency 圖
  2. 分 wave（wave = 無 dependency 鎖的 epic 群）
  3. Spawn 4 worker agent 併發（scripts/hooks/worktree-setup.sh）
  4. Wave 完成 → 整合測試 gate（E91）
  5. 下一 wave

典型

Phase 40 (6 epic, 全 parallel) = 1 個 wave 完成 · Phase 41 (3 epic) = 2 waves (E162+E163 → E164)

Deploy Pipeline

Pipeline · L4 · 7-gate 部署

/athena:deploy [env] 走 7 gate，任一失敗即 abort。驅動者：@deployer。

7 Gates

  1. CI 綠（tests + coverage + lint + e2e）
  2. No uncommitted changes
  3. On main branch（或 preview flag）
  4. Migration dry-run OK
  5. Pre-deploy guard pass（scripts/hooks/pre-deploy-guard.sh）
  6. Env vars present（VITE_API_URL build-time baked）
  7. Rollback plan recorded（deploy-log.md）

Phase 40 E159 會加

  • Gate 8 · GET /admin/sli baseline check
  • Gate 7 defense-in-depth · E156 contract conformance 重跑

部署目標

Zeabur（主）· Cloud Run（E121–E124 雙向 deploy guide）。Rollback 10 分鐘內透過 sre rollback（E159 CLI）。

PreToolUse

Hook · Tool 執行前

危險指令攔截。Exit code 語意：0 允許 · 1 擋 · 2 需人工確認。

典型

  • DROP TABLE / TRUNCATE
  • 無 WHERE 的 DELETE FROM / UPDATE
  • rm -rf 廣範圍刪除
  • Dirty deploy（uncommitted changes）

PostToolUse

Hook · Tool 執行後

Edit / Write / Bash 成功後自動跑。

典型 hook

  • ruff format / prettier（Edit 後）
  • bugfix-log 追加（fix: commit 時，E148）
  • Coverage gate（Bash 跑測試後）
  • Auto-promote check（E158 計畫 — 偵測 [GENERALIZABLE] 達門檻產 proposal）

人審 · Layer 5

永遠留給人的最後一哩

AI 做研究跟草稿，人做判斷跟承擔。 不管 pipeline 多自動，以下三個 gate 永遠留給人。

三 Gate

  1. /athena:plan 批准 — @strategist 提的 epic 人類點頭才進 EPIC_INDEX
  2. PR merge — CI 綠、coverage 過、Stop verifier 清，人類按合併
  3. /athena:promote --apply — 從 proposal 升級到 Tier 0 全球記憶

E164 autopilot（Phase 41 計畫）

Confidence ≥ 0.85 時自動推進 spec→implement→qa→commit→staging-deploy。Merge 和 prod-deploy 預設保持 pause。

/athena:plan approval

Human Gate · L5

@strategist 掃完 codebase 產出 Phase PRD + epic 提案。人類看完提案才按同意，才進 batch / loop。

為何不自動

  • 範疇判斷：哪個 epic 該進、哪個該延、哪個該拆
  • 優先序：business value 是 LLM 無法 independently 判斷的
  • 資源分配：哪 phase 先跑、哪 phase 等

PR merge

Human Gate · L5

即使 CI 綠、coverage 過、Stop verifier 清，merge 仍是人類的選擇。

人類要讀的

  • Diff — 特別是 SQL injection 邊界、型別錯位、schema 改動
  • Migration — 對應 E157 @dba signoff（若有 red flag）
  • Risk assessment — 部署時段、rollback 方案

E164 autopilot（計畫）

Merge 預設保持 human gate。AUTOPILOT_ALLOW_MERGE=1 才自動。
