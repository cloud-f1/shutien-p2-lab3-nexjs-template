# E63 — Alembic Autogenerate Normalization + Type Safety

> **Phase**: 20 — DBA Schema Management
> **Priority**: P0 | **Points**: 13
> **Depends on**: E62 (linter validates output)
> **Source**: Migrated from ai-clock-work E91 — `--autogenerate` emits inconsistent UUID types

---

## Problem Statement

The project's models use a custom `GUID` TypeDecorator (in `app.models.base`) that maps to native UUID on PostgreSQL and CHAR(36) on SQLite. However, Alembic's `--autogenerate` doesn't understand `GUID` — it introspects the DB column type and emits whatever it finds (e.g., `sa.UUID()` on PG, `sa.CHAR(36)` on SQLite). This leads to inconsistent UUID representations across migrations.

**Key design decision**: Migrations should use `sa.Uuid()` (standard SQLAlchemy 2.0 type), NOT the project's `GUID` TypeDecorator. `GUID` provides `process_bind_param`/`process_result_value` logic needed by the ORM layer, but Alembic DDL operations only need the dialect-level type.

## Stories

### E63-S01: `render_item` Hook in env.py (5 pts)

**Task**: Add a `render_item` function to `server/alembic/env.py` that normalizes all UUID-like types to `sa.Uuid()` in autogenerated output.

**Implementation Notes**:
- The `render_item` hook receives `(type_, obj, autogen_context)`
- When `type_` is `"type"` and `obj` is any UUID-like type (`GUID`, `UUID`, `PG_UUID`, `CHAR(36)`), emit `sa.Uuid()`
- Register via `context.configure(render_item=render_item)`

**Acceptance Criteria**:
- Given a model column using `GUID()` from `app.models.base`
- When I run `alembic revision --autogenerate -m "test"`
- Then the generated migration uses `sa.Uuid()` (not `sa.CHAR(36)`, `sa.UUID()`, or `GUID()`)
- And the E62 linter passes on the generated file

### E63-S02: `compare_type` + Type Equivalence (3 pts)

**Task**: Add `compare_type=True` to `context.configure()` in `env.py` with a custom comparison function that treats `GUID` ↔ native UUID as equivalent (prevents false-positive ALTER operations).

**Acceptance Criteria**:
- Given a model uses `GUID()` and DB column is native `uuid`
- When I run `alembic revision --autogenerate`
- Then NO spurious `alter_column` is generated (they're equivalent on PG)
- And if a column is genuinely `VARCHAR(36)` but model says `GUID()`, an ALTER IS generated

### E63-S03: Migration Template + Tests (5 pts)

**Task**: Customize the Alembic migration template (`server/alembic/script.py.mako`) to include standard imports and a comment header documenting correct patterns.

**Template adds**:
```python
import sqlalchemy as sa
# UUID columns: use sa.Uuid() (maps to native UUID on PG, CHAR(32) on SQLite)
# Boolean defaults: use sa.text("false") / sa.text("true")
# FK constraints: always include ondelete policy
```

**Acceptance Criteria**:
- Given I run `alembic revision --autogenerate -m "new feature"`
- When the migration file is generated
- Then it includes the standard comment header with correct patterns
- And a test verifies autogenerate produces valid, linter-passing migration code

## Risk Notes

- **Medium risk**: Modifying `env.py` affects all future migration generation
- **Backward compatibility**: Existing migrations using `sa.Uuid()` already work — no changes needed
- **GUID in models vs sa.Uuid() in migrations**: Intentional — models need GUID's value processing; migrations only need DDL types
